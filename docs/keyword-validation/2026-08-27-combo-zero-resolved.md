# 「多字組合的 0 不可靠」——這條規則太寬，2026-08-27 收窄了

> 原本的判讀邊界寫：「**多字組合的 0 不可靠**（Bing 不切組合）」，
> 因而有一批字被掛在「不知道有沒有量」的狀態。
> 這次把它量清楚了：**不可靠的只有「中文＋英數」那一種，中文＋中文的組合 Bing 切得出來。**

## 一、證據

`word` 本身 exact **63,864**、`履歷表` **2,628** —— 兩邊都很大。
但「履歷表 word」是台灣最常搜的組合之一，API 回 **0**：

| 中文＋英數（一律 0，**這個 0 不可信**） | 中文＋中文（切得出來，**這個 0 是實訊**） |
|---|---|
| 履歷表 word — 0（履歷表 2,628） | 履歷範本 — **831** |
| 報價單 word — 0（報價單 1,896） | 報價單範本 — **550** |
| 契約 word — 0 | 委託書範本 — **347** |
| word 範本 — 0 | 存證信函範本 — **49** |
| 離職證明書 word — 0 | 和解書範本 — **21** |
| 切結書 word — 0（切結書 958） | 切結書範例 — **399** |
| 委託書 word — 0（委託書 1,865） | 委託書範例 — **763** |

同一批字裡，中文＋中文的組合有量的還有：借據範本 **858**（比主詞借據 435 還大）、
收據範本 **647**、和解書範例 **341**、存證信函格式 **376**。

## 二、修正後的規則（三條）

1. **中文＋英數的組合（word／excel／pdf／英文詞）**：API 一律回 0，**完全不可信**，要另尋方法。
2. **中文＋中文的組合**：API 切得出來。**主詞有量而組合是 0，那個 0 就是實訊** —— 真的沒人那樣搜。
3. **主詞本身就是 0 的**：組合的 0 當然也是實訊，不必再懷疑。

⚠️ 另注意 `契約範本` broad 305／exact 0 —— **broad 與 exact 會分歧**，兩欄都要看。

## 三、把規則套回原本那批「不知道」的字

原本 17 個掛在「不可靠的 0」，套完只剩 **2 個真的不知道**：

### 3.1 仍然不知道（中文＋英數，2 個）

| 存證信函格式 word | 存證信函格式 376 | 同上，站上已有 `/citizens/certified-letter*` |

### 3.3 確定是 0：中文＋中文，主詞有量但組合沒人搜（4 個）

**這一組最值得看** —— 主詞很大，但沒人用那個說法搜：

## 四、這份改變了什麼

1. **不要再拿「組合的 0 不可靠」當萬用擋箭牌。** 只有中文＋英數那一種適用。
2. **「存證信函怎麼寫」是實訊 0**，連帶推翻「使用者會用問句搜書件寫法」這個假設 ——
   站上以「怎麼寫」命名的頁（`/writing/`、`/receipt/`、`/travel-expense/`）
   **靠的是主詞不是問句**，命名沿用沒問題，但**不要再為問句型另開新頁**。
3. **「公文範本」0 而「公文格式」300**：市場的詞是「格式」不是「範本」。
   站上 `/templates/` 標題用「公文格式 Word 範本下載」是對的，**「格式」兩個字不能拿掉**。
4. 借據範本 858 > 借據 435、收據範本 647 —— **「範本／範例」後綴在民間書件是主要搜法**，
   在公文則不是（公文範本 0）。兩個族群的命名策略應該不同。

## 五、怎麼重跑

```bash
node /root/seo-ops/bin/keyword-demand.mjs --file <候選字.json>
```
把主詞與組合**成對**放進同一個檔，才看得出是「真的 0」還是「API 切不出來」。
中文＋英數的組合，量到 0 一律不採信。
